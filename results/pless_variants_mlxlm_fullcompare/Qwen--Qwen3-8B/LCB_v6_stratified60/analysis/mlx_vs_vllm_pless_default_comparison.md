# mlx-lm vs vLLM: pless_default, Qwen3-8B, LCB_v6_stratified60 (60 tasks)

**Verdict.** pass@1 is equivalent within about ±2.5pp (Δ = +0.5pp, 95% CI [−2.0, +3.2], permutation p = 0.81).
mlx-lm is slightly lower at pass@5 (−2.6pp, p = 0.065) and pass@10 (−3.3pp, p = 0.49); neither is significant,
and both come from 6 tasks with few correct samples. This validates mlx-lm for **pless_default on Qwen3-8B only** —
not the G_k (`pless_renyi`) sampler and not Ministral.

## Setup

| | mlx-lm | vLLM (reference) |
|---|---|---|
| Model | Qwen3-8B bf16 | Qwen/Qwen3-8B |
| Sampler | pless (`bench/mlx_pless_logits_processors.py`), T=1.0, no top-p/top-k | pless, T=1.0, no top-p/top-k |
| Engine | mlx-lm `0.32.3.dev8+g0d4d3d04f`, 96GB Mac | vLLM, CUDA |
| Generation cap | 25000 tokens | 25000 tokens |
| Samples | 60 tasks × 10 | same 60 task_ids × 10 |
| Source | `../pless_default_{atcoder,leetcode}_think_t1.0.jsonl` (on the 96GB Mac; not in this repo) | `results/pless_variants_cuda/Qwen--Qwen3-8B/LCB_v6_stratified60/pless_default_*_think_t1.0.jsonl` |

- **Generation cap is inferred, not logged.** Records don't store `max_new_tokens`. Re-tokenizing every sample with the
  Qwen3-8B tokenizer gives max = 25000 on both sides and none above it (mlx: 114 of 600 at ≥24900; vLLM: 123).
- **mlx tasks come from more than one run.** 51 were generated by the v5 run (`architecture` =
  `sequential_groups_of_3_deep_row_capped_waves_v5`, 2026-10-28 19:36 → 2026-10-30 17:37 IST). 9 came from earlier
  runs with the same model, sampler and cap but different batching: 8 tagged
  `sequential_groups_of_3_default_completion_batch_size` (2828, 2869, 2952, 2955, 2999, 3047, 3225, abc305_d) and
  1 untagged (2756).
- **Eval.** Both sides re-scored in the same session on the main `uv.lock` machine (CLAUDE.md gotcha #9):
  `bench.eval --dataset livecodebench --skip-diversity --workers 4` (6.0s per-test timeout). The vLLM metrics here
  are that re-eval (`../metrics/vllm_reference_reeval/`), not the canonical file under `pless_variants_cuda/.../metrics/`,
  which can differ by ≤0.5pp from timeout noise.

## Significance (within-task permutation, 20,000 draws)

Under "backends equal", each task's 20 samples are exchangeable; mlx's 10 are drawn hypergeometrically from them.

| Metric | Δ (pp) | two-sided p |
|---|---:|---:|
| pass@1 | +0.50 | 0.812 |
| pass@5 | −2.65 | 0.065 |
| pass@10 | −3.33 | 0.488 |

- 39 of 60 tasks have identical correct counts; 11 favour mlx, 10 favour vLLM; net +3 correct samples of 600 for mlx
  (sign test p = 1.0). 36 of 60 tasks are saturated (0/10 or 10/10) on both backends.
- **Status counts (of 600 per side):** mlx Passed 422 / Failed 66 / ParsingError 81 / RuntimeError 19 / Timeout 12;
  vLLM Passed 419 / Failed 60 / ParsingError 92 / RuntimeError 19 / Timeout 10.

## What drives the hard pass@5 / pass@10 gap

pass@10 per task is 0 or 100 (any of 10 correct); pass@5 per task is 0 / 50 / 77.8 / 97.6 / ~100 for 0 / 1 / 2 / 4 / 5+
correct. On the hard subset each task is 1/20 = 5pp.

| Task | correct mlx / vLLM | pass@5 Δ contribution | pass@10 Δ contribution |
|---|---:|---:|---:|
| abc391_f | 0 / 1 | −2.50pp | −5pp |
| 3631 | 0 / 1 | −2.50pp | −5pp |
| 3466 | 2 / 4 | −0.99pp | 0 |
| abc342_e, 2952 | 6/5, 8/5 | +0.02pp each | 0 |
| **Hard total** | | **−5.95pp** | **−10pp** |

Two single vLLM samples account for 5 of the 6pp at pass@5 and all 10pp at pass@10. For a task with ~5% per-sample
success, P(0 of 10) = 0.95¹⁰ ≈ 0.60, so 0/10 is the most likely outcome even if the backends were identical.

All 6 low-count tasks (3354, 3466, 3471, 3631, abc333_d, abc391_f) favour vLLM, while mlx leads on several mid-range
tasks. *Unverified hypothesis:* mlx samples are slightly less diverse on hard tasks (would lower high-k pass@k
without moving pass@1). These data cannot separate that from noise.

## Implications

- A sampler change measured on mlx that moves pass@1 by more than ~3pp is distinguishable from the backend gap; a
  smaller one is not.
- Comparing new mlx G_k points against existing vLLM G_k points still puts this backend gap inside the k-sweep; a
  same-backend anchor point (e.g. re-run `gk_0_1` on mlx) is the safer design (todos E26).
